# Case study: a coding agent with memory (synthetic shop)

A small online shop, **Tidewell Goods**, and a coding agent that changes it. The
shop has a storefront, three analytics dashboards (customer behavior, marketing,
finance) and a traffic simulator. It cannot yet run A/B tests. Your agent builds
that, and the interesting part is how it knows what to touch.

The shop's code is stored in your memory as typed facts: what defines, calls,
reads and covers what, with file and line ranges. Beside it sit the team's own
decisions, incidents and earlier experiments. A question like *"what depends on
`shippingFor`?"* is then answered from memory in a few lines, and the agent opens
only the lines it was given instead of reading the repository.

Everything here is synthetic. No real shop, customer, order or incident is
described.

## Run it

You need Node.js 22.19 or newer, git, and na8ve agent signed in to your account.

**With na8ve agent**

```bash
git clone https://github.com/na8ve/case-study-coding
cd case-study-coding
na8ve-agent          # then: /login (once), and /demo coding
```

`/demo coding` seeds this folder into a space of its own (you confirm first),
switches to it, and asks the first question. Started in this folder, the agent
also finds the three skills in `.agents/skills/`.

**The shop itself**

```bash
npm start              # http://127.0.0.1:8080 and /admin for the dashboards
npm test               # the shop's own tests
npm run accept         # the A/B testing task: fails until you (or your agent) build it
```

On the admin page, **Simulate 1,000 shoppers** fills the dashboards with
deterministic traffic.

## The questions

1. *I want to A/B test the free-shipping threshold. What code would that touch,
   what could break, and what has gone wrong here before?*
2. *Build the A/B testing described in `docs/ab-testing.md`.* Then
   `npm run accept` tells you what is missing.
3. *Add an Experiments tab to the admin page.*
4. *Which of the three experiments should ship, and why?*
5. *Add a repeat-purchase view to the customer-behavior dashboard.*

## What a good answer does

- **Names what a change reaches.** For the threshold: `shippingFor`, what calls
  it, the routes that reach it, the tests that cover it, and the finance and
  marketing dashboards, which depend on it through the order's money fields.
- **Cites what the team wrote.** The rule that free shipping is judged on the
  discounted subtotal, the incident behind it, and what an earlier test of a
  discount did to margin.
- **Reads little.** It opens the line ranges memory gave it, not whole files.
- **Keeps memory true.** After an edit it runs `node tools/code-graph.mjs` and
  syncs (`cortex_code_sync`, or `/code sync`), so memory drops what the edit made
  false.
- **Judges on what the shop keeps.** A treatment that lifts conversion and costs
  margin is stopped, not shipped.

## What is here

| | |
|---|---|
| `src/`, `web/`, `server.mjs` | the shop |
| `sim/` | the traffic simulator: shoppers who react to the page and the price |
| `test/`, `acceptance/` | the shop's tests and the A/B testing task |
| `docs/` | **how memory works here** (`how-memory-works.md`), the task (`ab-testing.md`) and the metrics' definitions |
| `memory/knowledge/` | decisions, incidents and earlier experiments, as facts |
| `memory/code/` | the code graph, generated by `tools/code-graph.mjs` |
| `tools/hooks/` | optional git hooks that keep the code graph and memory in step at every commit (`git config core.hooksPath tools/hooks`) |
| `.agents/skills/` | how to change the shop with memory, build an A/B test, and build a dashboard |

`tools/code-graph.mjs --impact <name>` prints the same blast radius from the
local source, with no account needed.
